# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

This is a course deliverable repo for **CS2308.CH203 — Chuyên đề nghiên cứu và ứng dụng về Xử lý ngôn ngữ tự nhiên**. The whole repo revolves around one paper: **Self-RAG: Learning to Retrieve, Generate, and Critique through Self-Reflection** (Asai et al., ICLR 2024, arXiv:2310.11511, local copy at `paper/2310.11511v1.pdf`).

The work is split into two tracks defined in `SELF_RAG_SEMINAR_PROJECT_GUIDELINE.md` (the master planning doc):

1. **Seminar track** — present the paper (motivation, reflection tokens, training/inference pipeline, results, limitations).
2. **Final project track** — build a small **"Self-RAG-inspired" prototype**: a baseline RAG vs. a self-reflective RAG (retrieval-decision → relevance judge → generate → support judge → usefulness judge), compared on a QA dataset, without needing to fine-tune a model like the original paper (reflection signals are simulated via prompting/scoring rules instead).

**Current state: final-project implementation is underway** under `final/` (see `final/PIPELINE.md` for the concrete architecture/roadmap and its checklist for what's actually built vs. still planned). Most content documents are written in **Vietnamese**; keep diacritics correct when editing them.

- `final/notebooks/02_generator_baseline.ipynb` — Week-2 deliverable, the "Standard RAG" system (fixed top-5 retrieve → generate, no reflection). Loads the artifacts from notebook 01 (fails fast with a clear error if they're missing), re-defines `retrieve()` locally (notebooks are independent, no cross-notebook imports), and calls **Groq** (`groq` SDK, chat-completions style, key read from Colab Secrets as `GROQ_API_KEY` or env var locally). **Originally used Google Gemini** (`google-genai`, `gemini-2.5-flash`) but switched after the user's Gemini API key started requiring Google Cloud billing setup — Groq's free tier needs no billing. `GENERATOR_MODEL` is **not hardcoded** — cell-9 calls `client.models.list()` and picks the first match from a candidate list (`llama-3.3-70b-versatile` → `openai/gpt-oss-120b` → `llama-3.1-8b-instant` → `openai/gpt-oss-20b`), because a hardcoded `llama-3.3-70b-versatile` hit a real `model_not_found` even though Groq's own docs listed it as production — availability is account/time-dependent, so don't re-hardcode a single model name here. If Gemini free-tier access ever becomes viable again, swapping back touches cell-2 (pip install), cell-3 (key var name), cell-9 (client init), and the API call inside `generate_answer()` in cell-11. Generation is checkpointed to `final/artifacts/standard_rag_results.jsonl` one line at a time (resume-safe across Colab disconnects — reruns skip already-done `qid`s; a rerun also strips any leftover empty-answer records first, since the old "done = qid present" check used to permanently skip failed calls). Rate-limit handling reads the `Retry-After` response header on 429s rather than blind exponential backoff. Two distinct patterns were observed in practice and are handled differently: short `Retry-After` (seconds) is a normal per-minute limit, just waited out; long `Retry-After` (hundreds of seconds, recurring across many different questions) is a per-model hourly/daily quota exhaustion — `generate_answer()` detects this via `LONG_WAIT_THRESHOLD` (30s) and auto-fails-over to the next model in `CANDIDATE_MODELS` (tracked in `exhausted_models`, session-local) instead of sleeping for minutes. Remaining tunable knobs if still rate-limited: `SLEEP_BETWEEN_CALLS`, `RETRIEVE_K` (fewer passages → fewer tokens/request). `CANDIDATE_MODELS` is `["qwen/qwen3.6-27b", "openai/gpt-oss-120b", "openai/gpt-oss-20b", "groq/compound-mini", "groq/compound"]` — this account has no access to any Llama model on Groq (confirmed via `client.models.list()`, not just a guess), and the account's model list also includes non-chat models (`whisper-*` ASR, `canopylabs/orpheus-*` TTS, `meta-llama/llama-prompt-guard-2-*` a classifier) that cell-9 explicitly filters out via `NON_CHAT_PREFIXES` before picking `GENERATOR_MODEL`, so don't add those back in. Notebook 03 produces the analogous `self_rag_results.jsonl` for the Self-RAG-inspired system.
- `final/notebooks/03_self_rag_pipeline.ipynb` — Week-3 deliverable, the "Self-RAG-inspired" system (Hệ 3): all 4 reflection modules on top of the same retrieve/generate infra, independently re-defined (no cross-notebook imports, same convention as notebook 02) — including its own copy of the Groq client setup, `chat_models` filtering, and the `chat()`/`model_queue()`/`exhausted_models` rate-limit-failover machinery from notebook 02, generalized to take an arbitrary prompt (since 4 judge modules + the generator all need it, not just one generation call). `CANDIDATE_MODELS` dropped `groq/compound`/`groq/compound-mini` after a real failure: both silently route through `llama-3.3-70b-versatile` internally, which is blocked at the project level on this account (`403 blocked at the project level`) — always fails regardless of retry. Non-retryable 4xx errors (that 403 included) must `exhausted_models.add(model); break` to fall through to the next candidate, not `return ""` — an early version of both notebook 02 and 03 returned immediately on any non-5xx `APIStatusError`, which silently killed the whole call instead of trying the remaining models in the queue; fixed in both. Key design choices, deliberate not accidental:
  - **`[Retrieve]`** (`judge_retrieve`): LLM call returning `{"decision": "RETRIEVE"|"NO_RETRIEVE", "reason": ...}`; on unparseable output defaults to `RETRIEVE` (safe bias — real `train.json` questions essentially always need it).
  - **`[ISREL]`** (`judge_relevance_batch`): judges **all retrieved passages in one call** (a JSON array), not one call per passage as the paper does independently — a deliberate efficiency trade-off given the ~5x API-call multiplier already caused rate-limit pain in notebook 02; on unparseable/missing entries defaults to `RELEVANT` (safe bias — don't silently drop evidence to a parsing hiccup).
  - **Generator** (`generate_answer`): adaptive prompt — `WITH_CONTEXT_PROMPT` when there's post-`[ISREL]` evidence, `NO_CONTEXT_PROMPT` (answers from general knowledge, explicitly flags no specific citation) when `[Retrieve] = NO_RETRIEVE` or every passage got filtered out. This is the actual behavioral difference from Standard RAG (notebook 02), which always has fixed context.
  - **`[ISSUP]`** (`judge_support`): only invoked when `relevant_chunks` is non-empty; otherwise the orchestrator (`run_self_rag`) sets `NOT_APPLICABLE` directly rather than asking the LLM to judge support against nonexistent evidence.
  - **`[ISUSE]`** (`judge_usefulness`): always invoked, independent of whether evidence exists.
  - `extract_json()` strips ` ```json ` fences and falls back to a regex-extracted `{...}`/`[...]` substring before giving up, since Groq models don't reliably emit bare JSON despite being told to.
  - Same JSONL checkpoint/resume/empty-record-cleanup pattern as notebook 02, writing `final/artifacts/self_rag_results.jsonl` with one extra layer of fields (`retrieve_decision`, `isrel`, `relevant_aids`, `issup_label`, `isuse_label`, etc.) beyond notebook 02's schema.
- `final/notebooks/04_evaluation_report.ipynb` — Week-4 deliverable: builds the 3-way comparison table across No-RAG / Standard RAG / Self-RAG-inspired. No embedding/FAISS needed here (lighter, CPU-only) — article text for judging Standard RAG's support is reconstructed by re-loading `legal_corpus.json` into an `aid_to_article` lookup rather than re-deriving it from notebook 1's chunks. Key points:
  - **Doesn't assume all 250 dev questions completed** for notebooks 02/03 (realistic given the rate-limit history) — computes `common_qids` as the intersection of qids with a non-empty answer in both `standard_rag_results.jsonl` and `self_rag_results.jsonl`, generates No-RAG only over that intersection, then re-intersects with No-RAG's own completions (`final_qids`) before evaluating. The actual sample size is printed and stored (`So_cau` column), not assumed to be 250.
  - **No-RAG** is generated fresh in this notebook (reuses notebook 03's exact `NO_CONTEXT_PROMPT` wording for methodological consistency) — checkpointed to `final/artifacts/no_rag_results.jsonl`, same resume-safe pattern as notebooks 02/03.
  - **Three post-hoc judges applied uniformly across all 3 systems** — this is the metric notebooks 02/03 didn't have: `judge_correctness()` (new, compares generated answer against `train.json`'s human-written gold `answer`; labels CORRECT/PARTIALLY_CORRECT/INCORRECT) is computed fresh for all three systems. `judge_support`/`judge_usefulness` reuse notebook 03's exact prompt wording, computed **fresh** for No-RAG (support trivially `NOT_APPLICABLE`, no evidence) and Standard RAG (evidence reconstructed via `aids_to_chunks()` from its `retrieved_aids`), but **reused verbatim** from Self-RAG's own `issup_label`/`isuse_label` already stored in notebook 03's output — deliberate, not an oversight: same prompt/temperature=0 already computed there, recomputing would waste API calls without changing the number.

  - Also computes retrieval Recall/Precision/MRR in pure Python (no API calls) for Standard RAG (`retrieved_aids` vs gold) and Self-RAG **both pre- and post-`[ISREL]`-filter** (`retrieved_aids` vs `relevant_aids`) — the pre/post comparison is the quantitative evidence for whether ISREL filtering discards noise without losing gold-relevant articles.

## Self-RAG concepts worth keeping straight across sessions

Reflection tokens (the paper's core mechanism, Section 3 / Table 1):

| Token | Question it answers | Labels |
|---|---|---|
| `Retrieve` | Is retrieval needed at all? | Yes / No / Continue |
| `ISREL` | Is this passage relevant? | Relevant / Irrelevant |
| `ISSUP` | Is the answer supported by evidence? | Fully / Partially / No support |
| `ISUSE` | Is the answer actually useful? | Useful / Partially / Not useful |

Standard RAG: `Question → Retrieve top-k → Generate`. Self-RAG: `Question → decide Retrieve? → (retrieve) → judge ISREL per passage → Generate → judge ISSUP → judge ISUSE → final answer`. The recurring three-word summary used throughout the docs is **Adaptive Retrieval, Self-Critique, Controllable Generation**.
